==============================================

Physical display: 1440x3200, density 560

Purpose:
Validate cancellation, immediate restart and stale-result isolation before
integrating the Worker request core into production RequestAiRunner.

This is an isolated feasibility probe. It does not modify production chat or
use a real AI provider.

Retained test code:
- Request core under test: uni_modules/uni-ai-worker/utssdk/stream-request.uts
- Worker scenario: workers/markdownWorkerTask.uts,
  runCancelRestartScenario()
- Control/snapshot bridge: uni_modules/uni-ai-worker-probe/utssdk
- Automatic page: pages/repro-worker-capability/index.uvue

Protocol:
1. Worker starts request A against the six-event stream fixture.
2. Worker publishes request-tagged snapshots through the probe plugin.
3. The page polls immutable snapshots every 50ms.
4. After observing A's first event, the page sends restart-request with its
   send timestamp.
5. Worker aborts A and starts a separately tagged request B without a timer or
   scheduling gap. B targets the three-event stream fixture.
6. After B completes, Worker keeps a 1500ms observation window open before
   publishing the terminal assertion.

Network fixtures:
- A: POST https://request.dcloud.net.cn/api/http/contentType/eventStream?limit=6
- B: POST https://request.dcloud.net.cn/api/http/contentType/eventStream?limit=3
- enableChunked: true
- Expected B: 3 chunks, 177 bytes and contents 1, 2, 3 in order.

Assertions:
- A produces at least one event before the page sends restart-request.
- restart-request reaches Worker and B starts immediately after A.abort().
- No A data callback reaches application code after restart.
- No A success/fail callback reaches application code after restart.
- B returns exactly 3 chunks, 177 bytes and the expected ordered contents.
- The page observes an A snapshot and at least one B snapshot.
- The automatic sequence has no host timeout or isolation failure.

Conclusion:
PASS: three cold runs all cancelled A after its first visible event and started
      B in 0-1ms inside Worker.
PASS: B was complete and ordered in every run; no A data or terminal callback
      reached application code during the post-restart observation window.
PASS: the page-to-plugin-to-Worker control path took 5-6ms in these runs.

Evidence boundary:
- The counters prove that stale A callbacks did not cross WorkerStreamRequest's
  generation guard into application callbacks. They do not claim that the
  Android network stack produced no lower-level callback that was discarded.
- The 1500ms explicit observation window starts after B completes; the total
  A isolation interval was more than five seconds in each run.
- This uses a deterministic DCloud event-stream fixture, not qiniu or bailian.
- Real provider authentication, SSE variants, reasoning_content, [DONE], error
  payloads and long Markdown remain a separate gate.
- iOS and Harmony are not covered.
