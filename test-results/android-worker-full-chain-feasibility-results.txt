============================================

HBuilderX: 5.24.2026072917-dev
Compiler: uni-app x 5.24 vapor mode, bytecode view layer
Package: io.dcloud.ai.x
Custom playground version: 2.1.4
Device: Xiaomi M2102K1AC
Android: 14 (API 34)
Physical display: 1440x3200, density 560

Purpose:
Validate the complete mechanical path before integrating RequestAiRunner:
real Worker network -> RequestTask ArrayBuffer -> stateful UTF-8/SSE ->
incremental Markdown -> CMark -> minimal rich/image render descriptions ->
versioned snapshots observed by the page.

This is an isolated feasibility probe. It does not modify the production chat
request or claim that real AI provider compatibility is already verified.

Retained test code:
- Network and SSE core: uni_modules/uni-ai-worker/utssdk
- Worker scenario: workers/markdownWorkerTask.uts, runFullChainScenario()
- Snapshot holder: uni_modules/uni-ai-worker-probe/utssdk/index.uts
- Automatic page: pages/repro-worker-capability/index.uvue

Candidate bridge being tested:
- Worker posts cumulative snapshots with a strictly increasing version.
- The UTS plugin receives every Worker message and stores only the latest
  snapshot as an immutable JSON string.
- The page polls that string every 50ms and ignores an unchanged version.
- Cumulative snapshots make the final result lossless even if an intermediate
  snapshot is overwritten before one polling tick.
- This avoids relying on repeated UTS plugin success callbacks, which were not
  stable in the earlier direct-callback probe.

Network fixture:
- POST https://request.dcloud.net.cn/api/http/contentType/eventStream?limit=6
- enableChunked: true
- timeout: 12000ms
- Expected 6 network chunks, 354 bytes and 6 JSON data events.
- Expected first content: Chinese text meaning "This is message 1".
- Expected last content: Chinese text meaning "This is message 6".

Worker transformation:
- Each event content becomes one Markdown level-2 heading.
- The cumulative Markdown is parsed by CMark after every event.
- Every top-level token becomes a minimal render description:
  { key, kind: "rich" | "image", tokenType }.
- Keys use the top-level token index and token type. Every new snapshot must
  preserve all keys from the previous snapshot as an unchanged prefix.

Worker assertions:
- eventCount == 6
- snapshotCount == 6
- tokenCount == 6
- descriptionCount == 6
- descriptionKeys ==
  0:heading,1:heading,2:heading,3:heading,4:heading,5:heading
- stableKeys == true
- first and last Chinese content match the expected network events

Page assertions:
- At least 3 distinct snapshots are observed before terminal completion.
- Observed snapshot versions are strictly ascending.
- Terminal event, token, description and key values match Worker assertions.
- The actual observed versions were all six values: 1,2,3,4,5,6.

Conclusion:
PASS: the complete mechanical Worker chain is feasible on the tested Android
      vapor-mode runtime.
PASS: immutable cumulative snapshots cross the plugin boundary repeatedly;
      the page observed all six strictly ordered versions without loss.
PASS: CMark and minimal render-description construction stay off the page main
      thread and preserve stable keys across incremental results.

Not yet proven by this result:
- abort followed by immediate restart and stale-result isolation;
- actual qiniu/bailian authentication and real AI SSE variants;
- reasoning_content, [DONE], provider error payloads and long AI Markdown;
- production RequestAiRunner integration;
- iOS or Harmony behavior.
