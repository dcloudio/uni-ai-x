# libmark 在 Android / 鸿蒙平台的 Markdown 处理链路与差异分析

日期：2026-10-15

## 任务目标

全面梳理 Android 与 HarmonyOS 平台上 libmark 处理 Markdown 的逻辑链路，对比两端差异，重点说明
HTML / DATA / AST 三类输出的处理方式。

## 一、分层结构

```text
业务层   uni-ai-chat.uvue / uni-ai-x-msg.uvue        按 block.kind 分派渲染
  ↑
存储层   libmark-stream-store.uts                     stream entry、ops 应用、快照、重建
  ↑
运行时   uni-ai-worker-runtime/index.uts              收 op-batch、状态轮询、Sendable 边界
  ↑
Worker   aiRequestWorkerTask.uts                      libmark 会话 + 按行 feed
         aiPresentationWorkerTask.uts (仅 Android)    后处理与增量下发
  ↑
UTS 封装 uni_modules/libmark/utssdk                   平台分支
  ↑
原生桥接 native/android(JSON/JNI)  native/harmony(N-API)
  ↑
libmark  libmark-full.so (runtime + render + math + mermaid 插件)
```

两端共用同一份事件语义（`native/android/libmark_bridge_jni.cpp:1-12`、
`native/harmony/libmark_bridge.cpp:16-21`）：BLOCK→APPEND(1)、TAIL_PARTIAL→TAIL(2)、
TAIL_COMPLETE→COMMIT(3)、RESET→RESET(4)；kind 归为 `html/data/ast` 三通道，
带 `top_level_block_index` 对齐槽位。没有事件时返回 null/undefined。

## 二、Android 链路

1. 主线程 `RequestAiRunner`：
   - 内置 provider 走 `requestRemoteAiInWorker`（`requestAiRunner.uts:338`），Worker 内自己发 HTTP；
     自定义 provider 走主线程网络后 `appendAiWorkerMarkdown` 喂 Worker（`requestAiRunner.uts:169-173`）。
2. Worker（`aiRequestWorkerTask.uts`）：`WorkerStreamRequest`（`stream-request.uts`）收 SSE →
   `<think>` 拆分 → `feedLibmarkContent` → `processLibmarkContent` **按行切块** feed
   （`aiRequestWorkerTask.uts:219-238`）。
3. UTS 封装：`createSession('html', language, darkMode, background)` 返回 `{id}` 对象；
   `feedChunk` 调 Kotlin `LibmarkBridge`（`app-android/index.uts:20-49`），**JNI 边界传 JSON 字符串**，
   UTS 侧 `JSON.parse<LibmarkEvent>`。会话指针存在 Kotlin `ConcurrentHashMap<Int,Long>`
   （`LibmarkBridge.kt:17`），UTS 只见自增 id。
4. ops 攒批后 `flushLibmarkOps` 以 `{tag:'libmark-op-batch', ops}` UTSJSONObject post 给主线程
   （`aiRequestWorkerTask.uts:194-212`）。
5. 主线程 runtime：`receiveLibmarkOpBatchObject` → `pendingLibmarkOps`（`index.uts:217-233`）→
   通知 `pollWorkerSnapshot` → `takeAiWorkerOps` → `onMarkdownAstDelta` → `libmarkStreamApply`。
6. `libmarkStreamApply` 在 Android 分支只做 `prepareAndroidEntry`（微任务合批，
   `libmark-stream-store.uts:259-277`），随后 `sendAndroidEntry` 把 ops 转给**第二个 Worker**
   （`aiPresentationWorkerTask.uts`）。
7. presentation Worker：`LibmarkHtmlStreamAdapter.applyOps` 维护条目 → `nativeRenderBlock` →
   代码高亮/表格/脚注/引用/inline-math SVG 本地化 → 只回传**变化块的增量 changes（含 codeHtmlPrefix
   前缀补丁）**（`aiPresentationWorkerTask.uts:155-244`）。
8. 主线程接收增量 → `prepareNativeMermaidBlocks` → `notifyEntry` → `libmarkPresentationRevision++` →
   页面 `getMarkdownBlocks` → `uni-ai-x-msg.uvue` 按 kind 分派组件（`uni-ai-x-msg.uvue:20-36`）。
9. 完成：`libmark-complete` → `finishSession` → `libmarkStreamMarkComplete` →
   `prepareAndroidEntry(done)` → settled 后写 RenderSnapshot（`libmark-stream-store.uts:121-159`）。

## 三、鸿蒙链路

1. 主线程 `RequestAiRunner`：
   - 内置 provider 走 `requestRemoteAiInWorker`（`requestAiRunner.uts:338`），Worker 内自己发 HTTP
     （`WorkerStreamRequest`：`uni.request` + `enableChunked` + `onChunkReceived`）；
   - 自定义 provider 走主线程网络后 `appendAiWorkerMarkdown` → 以 `LibmarkChunk`（@Sendable 类）
     post 给 Worker（`index.uts:176-191`）。
2. Worker（`aiRequestWorkerTask.uts`）：内置 provider 走 `handleSseEvent`（SSE JSON → `<think>` 拆分，
   `483-522`）→ `feedLibmarkContent`；自定义 provider 走 `handleLibmarkChunk`（`272-291`），
   均按行 `processLibmarkContent` feed。
3. UTS 封装：`import bridge from 'libmark_bridge.so'`，N-API 直接透传，**native 直接构造 JS 对象
   返回**（`app-harmony/index.uts:15-30`）；会话句柄是 `napi_external`（`libmark_bridge.cpp:459-461`），
   GC finalizer 兜底销毁。
4. ops 攒批后以 `LibmarkOpBatch`（@Sendable + collections.Array）`harmonySendable:true` 发给主线程
   （`aiRequestWorkerTask.uts:185-192`、`app-harmony/sendable.ets`）。
5. 主线程 runtime：`receiveLibmarkOpBatch` → `pendingLibmarkOps`（`index.uts:200-215`）→
   `pollLibmarkState` → `onMarkdownAstDelta` → `libmarkStreamApply`。
6. `libmarkStreamApply` 在鸿蒙分支**主线程内直接** `adapter.applyOps` + `refreshEntry`
   （`libmark-stream-store.uts:428-431`）：全量 `libmarkHtmlBlocksToTextBlocks` → `prepareCodeBlocks`
   （携带上次 blocks 做增量高亮）→ 脚注/引用链化 → `prepareLibmarkHtml` → 表格预处理 →
   `prepareNativeInlineMathBlocks` → `prepareNativeMermaidBlocks` → `notifyEntry`
   （`libmark-stream-store.uts:207-237`）。
7. 完成：`complete-markdown` → `pumpLibmark` → `finishSession` → `AiWorkerState`（@Sendable）状态 →
   `libmarkStreamMarkComplete` → `refreshEntry(done)` → 持久化快照。

## 四、关键差异

| 维度 | Android | 鸿蒙 |
|---|---|---|
| 桥接形态 | JNI + Kotlin 包装；JSON 字符串跨边界 | N-API 模块（HAR）；直接 JS 对象，无序列化 |
| 会话句柄 | `{id}` → Kotlin 指针映射，显式 destroy | `napi_external`，显式 destroy + GC 兜底 |
| 编码 | 手工 UTF-16↔UTF-8（防 CESU-8，emoji 4 字节） | `napi_get/create_string_utf8` 直通 |
| 语言偏好 | UTS 值 + Kotlin **追加设备 LocaleList**（`LibmarkBridge.kt:44-50`） | 仅 UTS 传入值（Worker 用 appLanguage） |
| 字体加载 | API29+ 用 `AFontMatcher`（dlsym），失败回退候选路径 + `select_face` | 候选路径直读 + `select_face`（HarmonyOS Sans SC 等） |
| 网络位置 | 内置 provider 在 Worker 内，自定义 provider 主线程喂入 | 内置 provider 在 Worker 内，自定义 provider 主线程喂入 |
| 跨 Worker 传输 | UTSJSONObject 结构化克隆 | @Sendable 类（无拷贝） |
| 后处理位置 | 独立 presentation Worker（页面线程不阻塞） | 主线程同步完成 |
| 下发粒度 | 只发变化块 + 代码 HTML 前缀补丁 | 全量 textBlocks 重建（高亮增量） |
| 未闭合 table 预览 | 生成 `table` 预览条目（`libmark-html.uts:259-269`） | 降级为 `html` 预览条目 |
| 未确认源码预览 | 无（`libmark-source-tail.uts:14-16` 直接走 confirmed） | 有：`pendingSource` → `source` op → `data-text` 条目 |
| getBlocks 返回 | 引用 | 克隆（`libmark-stream-store.uts:439-444`） |
| 渲染 key | `slot:`+index（规避字节码复用残留） | `part.key`/`display:kind` |

## 五、三类 libmark 输出的处理

### html（正文通道）

- 桥接：未闭合 tail 用 `retain_tail_bytes` 保留前缀 + 拼接新载荷，**在桥内合成完整快照**再下发
  （两端一致）。
- 适配器：`appendHtml` 拆出已闭合 `pre/table/svg` 特殊块；tail 按内容特征分派——`<pre` →
  code/mermaid 预览、`<table`（仅 Android）→ table 预览、`<svg` → image、其余 → html
  （`libmark-html.uts:243-297`）。
- 展示：html → `uni-ai-libmark-html`（rich-text，两端都需要 `prepareLibmarkHtml` 补样式，仅发生
  位置不同）；code → 提取文本+高亮；table → `prepareMarkdownTable`；svg → base64 data URI 图片。

### data（信封通道，每次完整快照）

- envelope：`{type, status, source, svg}`；partial 走 TAIL，complete 走 COMMIT；同块二次提交按
  `blockIndex` 替换既有条目（`findDataEntryIndex`）。
- mermaid：DATA 会替换 HTML 通道里内联的 svg 条目（`findSvgEntryIndex` 合体，
  `libmark-html.uts:482-497`）。
- math：`status=='complete' && svg非空` 才算完成；两端最终都经 webview 光栅化为最终图片——Android
  由 presentation Worker 发起 `inline-math` 回环（`libmark-stream-store.uts:285-292`），鸿蒙在主线程
  `prepareNativeInlineMathBlocks` 直做。

### ast（保留但未启用）

- 两端桥接与 UTS 均支持 `mode:'ast'`（`DELIVER_AST | AST_PAYLOAD`，
  `libmark_bridge_jni.cpp:649-650`），插件渲染载荷随节点交付；但业务层所有调用均为
  `createSession('html', ...)`（`aiRequestWorkerTask.uts:166,344`），AST 通道实际未消费。

### source（上层自定义预览，非 libmark 原生 kind）

- 鸿蒙把未确认行级源码作为 `op:2/kind:'source'` 预览发给上层，适配器转成 `data-text` 条目；
  Android 刻意不做该预览，仅保留已确认 tail 的 patch（`libmark-source-tail.uts:13-25`）。

## 小结

两端共享 libmark 内核与"块级操作"协议，差异集中在边界技术（JNI/JSON vs N-API/Sendable）、
后处理执行位置（Android presentation Worker vs 鸿蒙主线程）、切换性能策略（增量补丁 vs 全量重建），
以及少数输出类型的兜底策略（table 预览、source 预览）。
