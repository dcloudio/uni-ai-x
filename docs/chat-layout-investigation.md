# 会话底部定位与布局稳定实验

## 启动性能回归的原因与后续检查

这次回归由两部分叠加：业务新增“等末条消息展示就绪才挂载”的整屏等待，并在挂载后调用最长 16 秒的点击追底循环；同时 Android 开发构建复用了旧原生插件，页面保存 v35 快照，Worker 却按 v34 校验，导致本地数据完整仍恢复失败、每次重建渲染资源。前者把等待和滚动直接暴露给用户，后者增加了实际准备耗时。

原生缓存遗漏证据限于此次 HBuilderX Alpha 5.37.2026112003 的 Vapor 自定义基座构建：缓存 manifest 记录原生入口摘要，没有记录 worker 子目录文件；只改 worker 内部版本后编译日志跳过插件。更改 utssdk/index.uts 摘要后重新编译，新 Kotlin 版本与页面一致，真机恢复成功。因此保留入口的 schema 版本注释，后续更改快照协议时同步更新入口并核对生成的 Worker，不能仅以页面编译成功或源码版本相同作为验收。

复发时按以下证据链检查：页面快照版本与原生 Kotlin 常量是否一致；运行日志是 assets restored 还是 assets saved；快照的主题、宽度、源文哈希与本地资源是否有效。避免靠删除用户数据或反复升级快照版本处理构建缓存问题。首屏定位和虚拟列表布局耗时另行验收，高度缓存不是本次修复前提。

## 工作方式

每轮只验证一个假设。简单对照在当前项目进行；涉及虚拟列表行为、测量和高度缓存的实验使用独立页面，并临时设为首页。验证通过再应用业务。测试不发送消息、不修改已有会话。临时入口和诊断日志不进入最终业务实现。

| --- | --- | --- |

| 非布局闪动 | 图片解码和组件复用状态不应显示旧内容 | 若尺寸稳定仍闪，再单独验证 |

## 实验 1：列表初始化到底

- 环境：HBuilderX Alpha 5.37.2026112003，Android 设备已安装自定义基座 io.dcloud.ai.x，Vapor bytecode。
- 改动前：强制关闭并重新打开，现有长会话显示顶部。
- 对照 A：仅增加 initial-scroll-bottom=true、scroll-anchoring=true；编译成功，产物包含属性，重新启动后仍显示顶部。
- 结论：不能据参考项目和属性文档就宣布业务修复完成。需要进一步区分组件初始化、scroll-top 绑定、异步数据和业务展示准备。
- 对照 B：临时首页 pages/diagnostics/chat-list-probe，固定 100 个 64px 条目，比较初始/异步数据、有/无 scroll-top=0。以 scrollHeight - viewportHeight - scrollTop 判断是否到底。
- 对照 B 结果：四组全部得到 top=12703.7138671875、scrollHeight=13538、viewport=834.2857055664062，底部误差约 0.00043px。说明初始化属性在当前基座有效；空列表后异步填充、有无 scroll-top=0 均能到底。这里只证明位置，未验证 64px 样式是否按预期应用，不把该实验作为高度精度证据。
- 已恢复正式首页并移除独立探针页；接下来临时记录业务列表在首次挂载及条目数量变化时的尺寸，确认是否是展示准备/区块放行改变了首次定位结果。
- 业务断点：首次 messages=2、rows=4、height=viewport=676.286、top=0；约一秒后 native settled=true，rows=6、height=5408.286，top 仍为 0。初始化发生在不完整展示结构上。
- 对照 C：末条历史展示数据就绪后才首次挂载列表。进入尾部，但布局修正后离底部约 147.714px。固定 scroll-into-view 到底部哨兵也未消除误差，已移除该尝试。
- 对照 D：在首次挂载后复用 scrollToLastMsg 进行有限校正；height=2126.857177734375、viewport=660.2857055664062、top=1466.5714111328125，误差约 0.00006px。强制停止后重开得到同样结果。
- 切换到已有 Markdown 会话：rows=10、height=1787.142822265625、viewport=660.2857055664062、top=1126.857177734375，误差小于 0.001px，截图显示末尾代码块及工具栏。
- 当前只锁存首次展示就绪；后续输出不会因为准备状态变化而卸载列表。不把所有历史的 readiness 作为挂载条件，避免与展示缓存容量限制冲突。
- 相关 Node 回归 18/18 通过。临时业务探针已移除；尚未解决历史图片加载门槛、测量缓存及追底算法优化，不能把位置通过当成无闪动验收。

## 实验 2：历史后文是否依赖视图图片加载

- 在真实 message-display 展示逻辑上模拟已有本地公式、图表资源和尺寸，但没有视图图片加载回调。修改前期望 3 个区块，实际只有 1 个，复现后文被阻挡。
- 为展示状态记录是否实际经历实时 processing。历史恢复不等视图图片加载回调；实时输出保留原有顺序门槛。
- 历史仍要求生成资源与尺寸、代码高亮等数据准备完成；不是无条件绕过所有就绪检查。
- 增加历史完整放行和未准备好资源仍阻挡的测试；相关回归 20/20 通过，原有实时等待测试仍通过。
- 在 Android 上运行现有本地完整 Markdown 示例（本地 runner，不请求模型），日志显示生成 11 个资源。强制关闭后重开，直接显示最终“以上就是所有 Markdown 语法的完整演示”及工具栏。此次新建的本地示例会话保留用于后续回归，未删除或覆盖既有会话。
- 使用现有 Alpha CLI 差量运行和 logcat app-android --mode lastBuild 验证，无相关编译/运行错误。
- 以上证据不等于所有闪动已消失。图片成功/失败/复用尺寸变化、列表项测量开销及缓存收益仍是下一轮独立实验，未实现高度缓存，也未重写现有追底循环。

## 实验 3：撤回启动等待与追底，检查快照恢复

- 用户报告实验 1 的 C/D 方案出现数秒转圈，显示后仍可见追底。位置最终正确不足以验收；撤回首次挂载就绪门槛、整屏 loading 和启动 scrollToLastMsg 调用，保留原生初始化属性与历史后文放行修复。
- 真机诊断：App Launch 后约 0.47 秒读取到快照，theme=light、width=412、version=35，环境匹配；约 0.71 秒恢复失败，约 3.80 秒重新保存 11 个资源。
- 从设备数据库只读导出核对：26 个完整区块、11 个资源，源文哈希正确，资源文件存在。问题不是历史数据不在本地。
- 构建产物发现 JS 快照版本为 35，原生 Worker 的 RENDER_SNAPSHOT_VERSION 仍为 34。原生插件缓存 manifest 仅列顶层 utssdk/index.uts 等文件，未列 worker/render-snapshot.uts；子目录改动被旧插件缓存遗漏。
- 在原生入口注明快照 schema 版本，触发插件重新编译；需要同时核对新 Kotlin 产物和真机恢复日志，不能只凭页面编译成功判定生效。
- 本轮相关 Node 回归 46/46 通过；高度测量与高度缓存未实施。
- 原生入口摘要变化后确实重新编译插件；新 Kotlin 的版本为 35。真机首次启动日志从 assets saved 变为 assets restored: count=11，App Launch 到恢复完成约 0.8～0.9 秒。
- 完整快照恢复后，单独 initial-scroll-bottom 仍会因虚拟列表估高和原生布局变化偏离底部；去掉 anchoring 也未解决，静态或首次 nextTick 设置 scroll-into-view 也未准确定位，已撤回这些尝试。
- 最终保留 initial-scroll-bottom，首次挂载最多 3 次读取列表总高度并无动画校正，期间用 opacity 隐藏尚未稳定的列表。不等待图片、工具栏就绪或后台渲染任务，不调用原有最长 16 秒的点击追底循环。触摸会取消校正并显示列表，会话切换使旧任务失效。
- 真机 3 次校正约 0.67 秒（不是 3×16ms；原生布局会占用主线程），整个完整示例从 App Launch 到显示末尾约 1.5～1.7 秒；6 次校正未发现收益，已缩为 3 次。最终末尾文字及工具栏截图通过。此结果仅覆盖当前 Android 开发基座的有效快照场景，不代表冷缓存重建或其他平台全部验收。
- 清理临时探针后差量编译、同步及强制停止重开再次通过；最终相关回归 48/48，HBuilderX logcat app-android --mode lastBuild 无相关错误。计时起点为应用 App Launch，未计入开发基座加载测试框架的时间。

## 实验 4：从顶部点击到底部的掉帧基线

- 时间：2026-11-21；代码基于 c0357be，保留工作区已有演示入口修改。Android 同一完整 Markdown 示例会话，系统显示模式约 120Hz，HWUI 柱状图保持开启。没有修改业务代码，没有重启或混入启动帧。
- 操作：用 ADB 连续向顶部滑动，确认首条用户消息可见；稳定后 reset gfxinfo，再点右下角按钮。使用 gfxinfo framestats 和 atrace gfx/view/input 采样；第一份跟踪额外开启 sched。三次都到达末尾，分别采得下表。百分比仅描述本次短操作窗口，不推算持续滚动 FPS；屏幕刷新率与系统每帧实际截止时间也不能混为同一阈值。

| 采样 | 渲染帧 | 错过截止时间 | P99 帧耗时 | Slow UI / bitmap upload / issue draw 计数 |
| --- | --- | --- | --- | --- |
| 1 | 37 | 4（10.81%） | 31ms | 4 / 2 / 2 |
| 2 | 36 | 4（11.11%） | 29ms | 4 / 2 / 2 |
| 3 | 44 | 5（11.36%） | 44ms | 3 / 3 / 2 |

- 第一份跟踪中最长主线程 doFrame 为 26.503ms，traversal 为 26.189ms。其中 RTView.preDraw 为 12.292ms，RTView.refreshTiles 为 12.039ms，RT.tileRaster1D 为 11.506ms；draw 为 12.350ms，其中 syncAndDrawFrame/postAndWait 约 11.3ms。这些是嵌套区间，不能逐项相加。
- 第三份跟踪再次看到 RT.tileRaster1D，单次最高 8.59ms；最长 traversal 为 18.20ms，其中 draw 为 16.81ms。RT.parseHtml 单次最高约 0.97ms、RT.layoutBlocks 约 0.82ms，不能把此次卡顿笼统归因于重新解析完整 Markdown 或测高度。
- 源码对应：uni-ai-md-text.uvue 使用 mode=native 的 rich-text。系统跟踪证实富文本瓦片栅格化、绘制和等待渲染线程参与长帧；本地消息/渲染快照齐全不等于原生绘制产物已驻留或无需重画。高度缓存不能直接消除这些绘制工作。
- 现有 scrollToLastMsg 在点击后读取 scrollHeight/视口高度，并按需写入 scrollTop，等待 16/50ms 后继续校正，最长 16 秒。它是否额外触发多次重建或放大瓦片工作，当前未做有/无校正的 A/B，不能宣布已证实。HWUI 图本身也有绘制开销，本轮所有采样保持开启，尚未量化其影响。
- 后续验证：先对照完整校正与一次跳转的同一操作，记录校正次数、目标条目与实际底部误差，不能以少画几帧但没到底作为优化通过；再隔离原生富文本冷/热绘制和复用成本。保持用户要求的高度方案暂缓。
- 原始证据保存在本机临时目录 chat-click-baseline-1/2/3.gfx，以及 chat-click-baseline-1/3.atrace；临时文件可能被系统清理，长期保留本节数值和结论边界。没有保留自动化钩子，也没有为此调整产品行为。
