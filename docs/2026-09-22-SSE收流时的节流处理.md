# SSE 收流时的节流处理

修改日期：2026-09-22

## 一、背景与目标

鸿蒙平台 AI 回答的 SSE 在主线程接收（`uni-ai-x/sdk/requestAiRunner.uts` 的 `onChunkFn`），每个 SSE event 都通过 `appendAiWorkerMarkdown` 直发一条 Sendable 消息给 Worker，由 Worker 内的 libmark session 增量解析。

服务端按 token 级流式返回时（常见 30~100 event/秒），存在两个放大效应：

- Worker 的 feed 次数与 SSE event 同频；libmark 的 tail 事件以"未闭合块整块快照"交付，长块流式期间会反复重发整块内容，产生大量重复解析与传输载荷；
- Worker 回传的 ops 按条投递，主线程 onMessage 次数随 ops 条数线性增长。

本次改造只针对鸿蒙平台：

1. SSE 收流按 100ms 周期节流合并，降低 feed 频率、ops 数量与 tail 重复载荷；
2. 一次 feed 产生的 ops 合并为一条消息投递，减少 Worker→主线程的 onMessage 次数。

## 二、节流语义

节流器有"空闲 / 活跃"两个状态：

- 空闲时收到消息：立即发送（首条不延迟），进入活跃，启动 100ms 窗口；
- 活跃时收到消息：仅累积，不发送；
- 窗口到期：本窗口有累积则合并发送一批，并保持活跃、启动下一窗口；整窗口无数据则退出活跃；
- 退出活跃后的下一条数据仍按"首条"处理。

| 时刻 | 事件 | 行为 |
| --- | --- | --- |
| t=0 | 收到 A | 空闲 → 立即发送 A，进入活跃，窗口 [0,100) |
| t=10 | 收到 B | 活跃 → 累积 |
| t=20 | 收到 C | 活跃 → 累积 |
| t=100 | 窗口到期 | 有累积(B,C) → 发送 B+C；保持活跃，窗口 [100,200) |
| t=110 | 收到 D | 活跃 → 累积（上一窗口有数据，未退出活跃） |
| t=200 | 窗口到期 | 有累积(D) → 发送 D；保持活跃，窗口 [200,300) |
| t=300 | 窗口到期 | 无累积 → 退出活跃 |
| t=450 | 收到 E | 空闲 → 立即发送 E，进入活跃，窗口 [450,550) |

持续有数据时，发送节奏收敛为每 100ms 一批；单条数据最长延迟 100ms；SSE 频率越高合并收益越大。

## 三、节流实现

文件：`uni_modules/uni-ai-x/sdk/requestAiRunner.uts`，全部以 `#ifdef APP-HARMONY` 隔离。

- 常量 `MARKDOWN_THROTTLE_INTERVAL = 100`；
- 状态字段：`markdownThrottleTimer`（0 表示空闲）、`throttledMarkdownContent`、`throttledMarkdownReasoning`；
- 方法：
  - `queueWorkerMarkdown(content, reasoningContent)`：空闲首条立即 `appendAiWorkerMarkdown` 并启动窗口；活跃期累积；
  - `onMarkdownThrottleWindow()`：窗口到期处理——有累积则发送并延续活跃，无累积则退出；
  - `flushThrottledMarkdown()`：发送当前累积并清空（收尾用，不延续窗口）；
  - `clearThrottledMarkdown()`：清理定时器与累积（不发送）。
- 接入点：
  - `onChunkFn` 的 `workerActive` 分支：鸿蒙调用 `queueWorkerMarkdown`，其他平台保持直发；
  - `finishRequest`：在 `completeAiWorkerMarkdown` 之前调用 `flushThrottledMarkdown()`，保证最后一段增量不丢失；
  - `stopWorkerRuntime`：所有终止路径（取消/错误/中止/请求切换/完成）统一调用 `clearThrottledMarkdown()`。

`<think>` 内容拆分等语义处理仍在 `onChunkFn` 内完成后再进入节流缓冲；发送仍携带 `workerRequestVersion`，Worker 侧的版本过滤机制保持不变。

## 四、ops 单次 onMessage 投递

同一批 ops 共享 `requestVersion`，合并为一条消息投递：

- `uni_modules/uni-ai-worker-runtime/utssdk/sendable.ets`：
  - 新增 `@Sendable LibmarkOpBatch`（`tag = 'libmark-op-batch'`、`requestVersion`、`ops: collections.Array<LibmarkOpEntry>`，方法 `pushOp(...)`）；
  - 新增 `createOpBatch` / `batchRequestVersion` / `batchCount` / `batchOp`；
- `workers/aiRequestWorkerTask.uts`：`flushLibmarkOps` 构造批次并只调用一次 `postMessage(batch, { harmonySendable: true })`（空批不发送）；
- `uni_modules/uni-ai-worker-runtime/utssdk/index.uts`：按 `tag == 'libmark-op-batch'` 单次接收，校验 `requestVersion` 后遍历解包到 `pendingLibmarkOps`，主线程消费（50ms 轮询 + 批量渲染更新）不变。

## 五、边界与兼容

- 其他平台（Android/iOS/Web/微信小程序）全部走原有直发路径，行为不变；
- 节流只在主线程收流环节生效，不改变 libmark 的解析结果与 block 增量语义；
- 终止路径统一清理，不会把上一个请求的累积数据发到下一个请求；完成路径先 flush 再收尾，不丢尾段；
- ops 批次携带 `requestVersion`，晚到/过期批次整体丢弃。
