# 会话记录持久化与重建方案优化

修改日期：2026-09-23

## 一、背景与问题

鸿蒙/Android 平台上，会话重启（冷启动）后历史 AI 消息显示为 Markdown 源码（公式显示 LaTeX 原文）。同时在鸿蒙真机实测中，历史会话重建时主线程有明显卡顿。

## 二、根因分析

1. 运行环境隔离：vapor 模式下页面运行在 JS 引擎中，UTS 插件运行在原生环境中（见官方文档 `tutorial/compatibility.md`）。页面无法直接调用 libmark 这类依赖原生实现的 UTS 插件，主线程调用会抛出 `ReferenceError: LibmarkBridge is not defined`，导致 body 重建失败、回退为原文显示。
2. 主线程同步重建成本：在可调用 libmark 的平台（鸿蒙）上，主线程同步解析大段 body 会阻塞 UI 渲染，长消息恢复时卡顿明显。
3. 存储层面：鸿蒙 `uni.setStorageSync` 为 preferences `putSync + flush()`，每次写入整文件刷盘；持久化含 SVG payload 的大 AST 在长会话下写放大明显。

## 三、修复方案

### 3.1 总体思路

持久化只保留轻量原文（`body`），渲染数据不落 storage；重启后由原文重建渲染 blocks，且重建统一在 Worker 中执行（Worker 运行在 UTS 原生环境，可调用 libmark，且不阻塞页面主线程）。

数据流：

- 流式阶段：Worker（libmark 解析）→ ops → 页面 `streamEntries`（内存 LRU）→ blocks
- 恢复阶段：页面请求重建 → Worker（libmark 解析 body）→ ops → 页面应用（去重、失败防重试）→ 触发重算

### 3.2 具体实现

1. 持久化与停止路径（`sdk/index.uts`，维持既有方案）
   - `updateMsg2Storage` 为固定 2 秒节奏节流（窗口内不重置定时器）；
   - 新增 `flushMsg2Storage()`：完成/停止/中断时立即落盘最终状态；
   - `onState('completed')` 不再序列化 AST，只刷新完成态并落盘；
   - `abortRequest` 在中断前对当前流式消息置 `rendered = true` 并落盘。
2. 数据迁移（`sdk/storage-manager.uts`，维持既有方案）
   - 新增 `uni-ai-storage-version`（当前 2）；
   - 打开会话时若版本低于当前，清空该会话消息的 `markdownAst`/`markdownHtml`（内存立即生效），后台按 200ms/条重写 storage，全部完成后写入版本号（幂等）。
3. Worker 重建链路（本次修复）
   - Worker 侧（`workers/aiRequestWorkerTask.uts`）：新增 `rebuild-markdown` 消息处理，使用独立 session（createSession → feedChunk → finishSession）解析完整原文，解析结果以 `libmark-rebuild-ops` 消息回传；解析失败回传空 ops。
   - Runtime 侧（`uni-ai-worker-runtime`）：新增 `requestAiWorkerMarkdownRebuild`、`setAiWorkerRebuildListener`；Worker 未就绪时重建请求排队，`ready` 后统一冲刷；回包通过监听器分发，无监听器时暂存待消费。
   - SDK 侧（`sdk/libmark-stream-store.uts`）：新增 `libmarkStreamRequestRebuild`（in-flight 去重、失败标记防重试）与 `libmarkStreamApplyRebuild`（应用 ops 并校验 blocks，空则标记失败）；移除页面侧对 libmark 原生插件的直接调用。
   - UI 侧（`uni-ai-chat.uvue`）：注册重建回包监听，应用成功后递增 `rebuildVersion` 驱动列表重算并触发滚底刷新；渲染入口在 Android/鸿蒙上补充「body 非空即可进入重建」判断，覆盖无 `libmarkRevision` 的历史消息。
4. 平台范围
   - 重建链路覆盖鸿蒙/Android；iOS/Web/微信小程序保持原有 cmark 持久化逻辑不变。

### 3.3 关键参数

| 参数 | 取值 |
| --- | --- |
| body 持久化节流间隔 | 2000ms |
| 旧消息重写间隔 | 200ms/条 |
| streamEntries LRU 上限 | 200 条 |

## 四、执行记录

### 4.1 改动文件

| 文件 | 内容 |
| --- | --- |
| `workers/aiRequestWorkerTask.uts` | 新增 `rebuild-markdown` 消息处理与 ops 回传 |
| `uni_modules/uni-ai-worker-runtime/utssdk/interface.uts` | 重建请求/结果/监听器类型定义 |
| `uni_modules/uni-ai-worker-runtime/utssdk/index.uts` | 重建请求 API、回包分发、未就绪排队、监听器管理 |
| `uni_modules/uni-ai-x/sdk/libmark-stream-store.uts` | 重建请求/应用函数（去重、失败标记），移除页面侧原生调用 |
| `uni_modules/uni-ai-x/components/uni-ai-chat.uvue` | 重建回包监听、入口条件补充、移除原主线程重建队列 |

### 4.2 实现要点

1. Worker 重建使用独立 session，与流式协议状态完全隔离，可与 AI 请求并发执行。
2. 页面重建请求带 in-flight 去重；重建结果为空或应用后无 blocks 均标记失败，本次会话不再重试，界面回退原文显示。
3. 重建成功后主动触发一次滚底刷新，规避列表内容高度突变时首帧原生视图未重绘的问题。
4. UTS 插件产物（`classes.dex`）随程序文件同步并动态加载，修改插件后运行即可生效，无需重做自定义基座。

## 五、验证结果

Android 真机（vivo V2314A，自定义基座）：

| 场景 | 结果 |
| --- | --- |
| 冷启动加载历史会话（无 ast/html，由 body 重建；含公式/流程图/长文本） | 富文本正常渲染 |
| 冷启动加载无 libmarkRevision 的历史消息（标题/加粗/列表/行内代码/代码块） | 富文本正常渲染 |
| 公式重建（行内、单行块、多行块；含流式消息强杀后重启） | 均渲染为 SVG 图片 |
| 连续二次冷启动（重建可重复） | 正常 |
| 编译 | `项目 uni-ai-x 编译成功` |

备注：公式 `$$...$$` 紧跟在列表之后时，libmark 会将其解析为纯文本（独立段落或前后非列表时正常）。重建与流式共用同一解析链路，该行为由 libmark 解析决定，非本次改造引入。

鸿蒙平台构建通过（hvigor 制作运行包成功），真机验证通过，代码与 Android 同构。
