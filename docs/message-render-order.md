# 消息按顺序渲染的约束与实施方案

## 本次已实现：工具栏的一秒从何时开始

最后一条 AI 消息满足以下条件后，等待一次 `nextTick`，再开始一秒稳定期：

- 请求结束或被停止，且消息具备完成标记或工具结果。
- 原生 Markdown 展示层已提交最终准备结果；停止回答也执行展示层收尾。
- 已登记的异步工作全部结束，包括代码高亮、公式/图表生成、SVG 文件准备，以及挂载中的公式/图表图片加载。
- 没有待确认的日历操作，工具栏处于允许显示的状态。

正文、思考、搜索状态、工具状态、主题、展示版本或异步任务发生变化，立即取消倒计时并隐藏最后一条消息的工具栏。条件再次满足后重新等待一秒。倒计时和 `nextTick` 回调都有版本校验；卸载、消息复用后的旧回调不能显示新消息的工具栏。失败回调结束任务，采用现有失败展示；删除消息会清理任务。

这一秒是收尾的稳定期，不能充当“异步工作已经完成”的判据。当前实现依赖应用可观测的展示状态和任务，不代表操作系统已把所有像素绘制到屏幕，也没有覆盖任意 rich-text 内远程图片的加载事件。rich-text 没有逐张图片加载完成事件；这类资源需要下文的统一资源准备阶段。历史消息仍保留原有的工具栏显示策略。

## 总体约束

自动输出时，只允许最后一个可见区块继续增长。只要下一个区块已经显示，前一个区块的内容、类型、高度、间距和折叠状态就必须冻结。

网络接收、Markdown 解析和资源准备可以并行；可见内容只能从上往下提交。用户主动展开、查看源码、重试或切换主题属于显式操作，需要单独保存阅读位置。

## 从固定字段顺序改为事件顺序

当前 `thinkContent → body → toolStatus` 的聚合展示不能表达多轮调用顺序，应保留它们用于存储兼容，但新增按发生顺序记录的展示区块：

```text
思考第 1 轮 → 正文第 1 段 → 搜索/工具第 1 次 → 思考第 2 轮 → 正文第 2 段
```

每个区块有稳定的 `blockId`、请求代次、轮次、递增序号和版本。新一轮思考、新搜索、新工具调用只能追加区块；不得重新打开顶部旧思考或新增全局顶部搜索行。消息级来源集合继续作为引用元数据，不决定顶部区块的插入。

## 用统一提交器控制可见范围

区块状态为：接收中 → 输入封口 → 准备中 → 就绪 → 提交冻结；准备失败则进入就绪的终态降级内容。

维护两个位置：接收位置表示数据已到哪里，提交位置表示前面连续就绪的区块已显示到哪里。后方区块即使准备好了，也不能跨过未完成的前方区块显示。

- 普通文本可以在尾部逐步显示；解析器确认段落不再被后续输入重解释，并完成布局准备后，才允许显示下一块。
- 代码、表格、公式、图表和图片进入统一资源准备流程。最终类型、内容、样式和尺寸确定后，才能放行后文。
- 图表慢时，加载提示属于当前尾部区块；后文继续接收并缓冲。不能在已有后文的中间把源码或占位图换成不同高度的图表。
- 异步回调只提交准备结果，不能直接修改已显示的区块。提交器校验消息、请求代次、区块版本和终态，拒绝过时结果。
- 完成工具栏、来源列表等收尾区块只能在最后正文冻结后追加。工具栏额外保留本次修正的一秒稳定期。

提交应批量更新连续就绪区块；不要为了逐块推进反复扫描全文、序列化 AST 或重建所有列表项。

## 各类区块的处理规则

| 区块 | 允许自动变化的范围 | 后续内容显示后的规则 |
| --- | --- | --- |
| 思考 | 当前轮次的尾部思考区 | 封口冻结；后续思考另开一块，不自动收起旧块 |
| 搜索、工具状态 | 当前尾部操作区 | 在尾部先结束/移除进度提示，再显示后文；要保留操作摘要则冻结为终态 |
| Markdown 段落、列表、表格 | 当前未封口的尾块 | 类型与布局冻结；不能因后续定义或解析结果回头替换 |
| 代码高亮 | 尾块内准备、分批提交 | 最终高亮和行高确定后放行后文，不再后台改写旧代码块 |
| Mermaid、块公式、图片 | 尾块内生成与加载 | 准备好最终表现后放行后文；失败固定为源码或错误终态 |
| 引用、脚注 | 提交前确定标记的文字和占位 | 后续只更新点击后打开的详情，不改变已显示标记的宽高 |
| 错误、中止 | 当前尾块收尾并追加状态 | 保留已提交内容，不把整段已有正文替换成错误卡 |

Markdown 的“封口”需要解析器保证。引用式链接/图片等可能在后文才出现定义，不能仅因收到换行就认定前文稳定：应延迟提交受影响的块，或冻结为原始文字并在详情中解释，禁止事后回写已提交区块。选择哪一种需要产品确认。

## 失败、停止、复用和历史恢复

- 每种准备任务有明确成功/失败回调。超时是进入固定降级终态的决定，不是未经确认就把任务视作成功；进入终态后，迟到的成功结果不得替换旧块。
- 停止时取消未提交任务，冻结可见尾块，丢弃尚未显示的后方缓冲，再显示终止状态和工具栏。
- 重试创建新代次；旧回调、旧列表组件的加载事件不能修改新代次。
- 历史消息优先使用最终展示快照。没有可用快照时，先准备所需内容再提交；不要让上方历史消息在用户阅读下方时从加载占位突然变成长文。
- 主题、宽度改变会使旧布局失效，应批量准备替换内容，并按区块 ID 和块内偏移恢复阅读位置。

## 建议实施次序与验收

1. 引入展示事件区块，先改思考、搜索和工具状态，消除固定顶部回写和正文下方移动的状态卡。
2. 引入统一准备任务与连续提交位置，接管图表、公式、图片、代码和解析器的块替换。
3. 收口错误、中止、历史恢复和主题变化，删除各组件绕过提交器更新内容的路径。

验收场景包括：正文后再次思考、先说一句再搜索、连续多轮 MCP、慢图表后紧接长文、公式加载失败、未知尺寸远程图片、后置引用定义、中途停止并重试、旧回调晚到、历史消息恢复。

核心断言：自动输出期间，除唯一可变尾块外，所有可见区块的顺序、内容版本、顶部位置和高度保持不变；后方就绪区块不能越过前方未就绪区块；工具栏只在连续提交位置到达消息终点且稳定一秒后出现。

本次只实现工具栏收尾条件；本文件的区块事件、统一提交器和资源准备流程尚未实施。

## 用户主动滚动

列表不默认滚底，也不在请求开始、流式更新、重建完成、输入框聚焦时滚底。移除持续跟随开关、原生滚动锚定和初始化滚底。后续内容增长只更新按钮可见状态。

早期固定坐标版本的 Android 真机验证中，点击后停在约 1927px，新增内容未继续触发滚动，确认取消了持续跟随。这是历史验证记录，不代表下述最终校正算法已通过一次到底的真机验收；其他平台也尚未实机验证。

固定坐标方案能停止跟随，但虚拟列表的未测量项会使 `scrollHeight` 偏小，造成一次点击不到底。参考 DCloud APP 的 Uni-IM-X 按实际列表高度滚动的做法，这里只保留一个点击函数：读取剩余距离、滚动、等待一帧后重新测量；连续两次已到底即结束，最多 30 次，用户触摸、会话切换和卸载可取消。关闭动画，避免校正尚未到达的动画目标。没有持续锚点、独立布局轮询器或输出更新触发器。回归测试模拟首次跳转后总高度被虚拟项重新修正，并验证完成后新增内容不再跟随，以及触摸和会话切换取消。最终算法的模拟测试已通过，但真机一次到底的结果仍有异常，尚待用户验收。

## 冷启动回归与列表边界验证

冷启动走原文重建时，若消息包含不支持高亮的 Bash 代码，旧原生高亮逻辑会保留源码，却不报告代码准备结束，导致最后一条消息的工具栏一直等待。失败分支必须提交原文终态并更新完成标记；新增测试贯穿历史状态 `none`、混合支持/不支持语言的 Worker 准备和工具栏的一秒延迟。该原生代码需要进入新的自定义基座，页面热更新和清理页面构建缓存不能替代基座更新。

工具栏独立列表项在等待期间预留最终的 42px 高度。真机上，长文恢复后零高度列表项会出现准备已完成但工具栏仍不可见的问题；预留高度后，恢复快照、滚动到底部均可正常显示，也避免延迟结束时新增工具栏高度。

关闭自动跟随后另一个复用问题暴露出来：真机日志显示，公式 `uni-ai-md-e9` 已结束加载、工具栏已就绪，滚动复用后同一资源又登记为等待；组件没有卸载，离屏图片也没有再次回调，工具栏便一直隐藏。资源首次加载结束后按消息与资源标识记住终态，同一图片的视图复用不再重开消息级任务；主题或图片内容改变仍等待新资源，释放消息时清除记录。新增回归测试覆盖重复加载、新资源、跨消息与清理。

Android/Web 的消息列表已移除覆盖整个聊天区域的绝对定位，也不再用输入区高度构造列表底部占位。消息列表与原有圆角输入区使用正常上下布局，滚动到底部按钮以列表自身底部定位。Android 真机测量中，普通状态的列表底部与输入区顶部均为约 766px；键盘弹出后均为约 469px，两个区域不重叠。临时测量日志已移除。

## 滚底按钮与示例数据

滚底按钮原先要等内容更新停止 180ms 才测量，测量后又延迟 180ms 显示；连续快速输出会反复重置计时，加上 60/30px 的底部阈值以及滚动时隐藏条件，内容超过一屏时按钮仍可能不可见。现改为下一次视图提交时合并检查，距底部超过 1px 即显示，并移除滚动时强制隐藏。此项仅完成静态检查，按用户要求交由用户测试，未运行新的设备验证。

完整 Markdown 示例保留十列表格和可横向滚动的代码长行，移除过量重复字符。完整示例按 50ms 分批、约 3.5 秒发送完正文，用户已观察到提速；异步图表收尾与工具栏稳定期不包含在正文发送时长中。其他压力场景保留原有速度。

可横向滚动容器已声明横向方向，但纵向手势被吃掉的问题尚未可靠定位或修复，暂按疑似框架 bug 记录，不计入已解决问题。
