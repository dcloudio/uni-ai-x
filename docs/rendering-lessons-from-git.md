# 从 Git 历史提炼的渲染与框架使用注意事项

历史整理日期：2026-11-19，原代码基准 `f44b82d`；2026-11-20 补充本轮修复与真机验收。

梳理范围为当前分支可达的 642 条提交，以及所有本地引用可达的 774 条提交，时间跨度从 2025-05 至 2026-11。全量检索提交标题和正文，对相关实现、修复反转及历史报告进一步查看 diff，并抽查当前代码。合并、移植和备份分支中的重复记录不重复算作独立结论。没有逐条重测历史问题，也没有重新测试当前框架。

下列内容是本项目的设计与实现约束，以及有版本范围的兼容经验。提交里出现过某个问题，不代表最新版框架仍存在这个问题；历史报告中的性能数值不能当成当前版本的性能数据。

## 一、优先遵守的设计约束

### 1. 展示组件不要承担重复的数据准备

Markdown 解析、高亮、HTML 转换、表格尺寸计算、公式图表生成及缓存写入，应尽量放在消息准备层或合适的后台任务中。组件主要读取准备好的展示数据。

列表回收后重新挂载是正常行为。如果这些工作放在组件挂载、每行 watcher 或渲染计算里，滚动本身就会重新解析、生成图片、测量窗口甚至写存储。

依据：`c1dafd6`、`b9858cf`、`a1effb3`、`f02a2eb`、`10aab3f`。这些提交的验证程度不同，部分仅静态检查；它们支持职责划分，不能统一解释为已测得帧率提升。

### 2. 解析进 Worker，不等于整个展示链路已经离开主线程

HTML adapter、token 转 HTML、表格准备、引用脚注处理、JSON 编解码、资源 IO，以及最后的原生布局、绘制和图片解码，都可能继续阻塞界面。需要分别判断成本所在。

Android 后续将展示准备和后处理下沉，并只回传变更块；主线程仍负责视图提交。`a133b29` 中 512 行场景的卡顿帧比例下降，但 2048 行场景 P95 仍为 200ms；`df0d7aa` 的进一步下沉也没有测得额外帧性能收益。不能仅凭“用了 Worker”宣称问题解决。

依据：`78ec6d7`、`04358fb`、`a133b29`、`df0d7aa`。

### 3. 流式处理需要合并更新，并保证最后一批必达

不按每个网络 chunk 立即全量解析、序列化和发布；合并过密更新，跳过相同内容，结束时强制刷新尾批。同一代码块积压多个版本时，优先收敛为执行中任务和最新待处理任务。

不同阶段采用过 300ms、48ms、64ms 等节奏，这些是当时实现参数，不是可跨场景照搬的最优值。单纯把间隔改大，也可能只让回复变慢。

依据：`78ec6d7`、`04358fb`、`4658ee6`、`a133b29`。单次请求还应复用有状态解码器，避免反复分配以及多字节字符跨分片出错：`d13c02f`、`f5a8f14`。

### 4. 一条消息变化，不应使全部历史消息重新准备

缓存失效按消息和版本控制；未变化的块、行对象和参数数组保留身份。避免在流式热路径里深度监听整段会话、序列化全部来源、深拷贝完整 AST，或每次生成全新的列表参数。

依据：`0032dcf`、`3f1a887`、`e64c9a1`、`df0d7aa`。当前工具栏也仅由工具栏行订阅正文和任务变化，避免每个正文分段各自订阅：`311e45a`。

### 5. 正文之外的状态变化也必须计入布局稳定性

思考、搜索状态、工具卡、图表和工具栏都可能改变消息高度。网络完成不是展示完成；工具栏应在可观测的展示准备结束后，再连续稳定一秒出现，期间有变化就重新计时。

当前工具栏已登记高亮、公式图表和挂载图片任务，失败也应进入终态。它仍不能观测任意 rich-text 远程图片的逐图加载，更不能证明所有像素已经绘制。

依据：`4da0299` → `311e45a`。本轮 `2a280ff` 已实现保守可见前缀冻结和迟到思考/搜索尾部追加，完整持久化事件协议仍未实施，见 [消息顺序渲染方案](message-render-order.md)。

## 二、原生 RichText 与节点使用

| 注意事项 | 做错后的表现及应对 | 历史依据与边界 |
| --- | --- | --- |
| 不要持续全量改写大 RichText | 历史 Android 实验中，持续修改 nodes 会反复布局和生成大位图；固定 RichText 的存在本身并非同等瓶颈。应减少更新范围与次数，并控制内容尺寸。 | `4e4a53f`、`14445cf`；来自 HBuilderX 5.23/5.24 的历史实验，不代表当前基座已重测。 |
| 不要简单把每行代码拆成一个原生 RichText | 高亮可以逐行准备，但视图逐行增加会放大节点数和布局成本。本项目后来改为一个 RichText 承载代码块，并保留空行占位。 | `ebce345`；后续优化应同时评估单块位图尺寸，不能反过来无限合并整篇消息。 |
| 保留复杂块的列表边界 | 代码、表格、公式、图表等需要独立布局、滚动及复用边界；不应为减少节点把整条复杂消息重新装进一个巨大列表项。 | `c2960d9`、`4823de3`；后来也有连续普通富文本合并，说明边界应按结构和成本确定。 |
| 不要随意删除 `disable-split-screen-render` | 项目为相关原生 RichText 显式开启该配置，目前代码、表格等仍保留。修改时应单独验证流式与回屏效果。 | `e5bf057` 只记录了设置行为，缺少足以证明普适因果的说明，不能据此认定它对所有页面都更快。 |
| `flatten` 不能加在事件承载节点上 | 拍平后可能没有独立原生节点，点击、触摸、预览、复制、展开收起失效。只对已确认安全的纯展示叶子使用。 | `e4025a5` → `b82e385`。 |
| `flatten` 不能替代裁剪、层叠和结构边界 | 历史最小复现确认 flatten 父 View 与原生 RichText 组合会破坏父级圆角裁剪；不能靠内容自身圆角代替横向视口裁剪。 | `5b7204c`、`b894ed3`、`a2b4ede`；当时 Android 14 / HBuilderX 5.24 已复现，当前框架状态未重测。 |
| 不要跨平台批量拍平组件链 | 鸿蒙曾因页面、消息容器和 Markdown 结构节点过度拍平，丢失列表标识、引用及分割线。编译成功不足以证明画面正确。 | `a8a32e7` → `4299104`；最终缩回安全静态叶子。 |
| RichText 内部排版要单独核对 | 根节点固定小行高会裁掉大标题；空白 HTML、空代码行可能折叠；源码空格、缩进和换行需要明确保留。 | `1b2942f`、`b5f1444`、`790e6fd`、`ebce345`。不要把某一代渲染器的 CSS 配方直接搬到另一代。 |
| 简单装饰不要制造重复绘制 | 页面已有主题背景时，避免列表、行容器、导航和内容层重复铺同色背景。分割线等可使用简单原生展示。 | `1c53cac`、`73d200e`；代码、表格等有语义的底色仍需保留。 |

## 三、列表复用、响应式和异步生命周期

| 注意事项 | 做错后的表现及应对 | 历史依据 |
| --- | --- | --- |
| 列表的 `type` 按展示结构划分，数量有界 | 工具栏、代码、公式、普通正文等不应混用不兼容的复用结构；首行有头像时也要区分。不要为每条消息创建独立复用池。 | `54120cc`、`fd6302d`。 |
| 外层行 key、内层子树 key 与业务身份职责不同 | 内层 key 每次跟消息变化会销毁重建；但有状态或异步组件又不能只用一个通用 key。应允许已确认无状态的同类子树复用，同时按业务身份重置状态。 | `2aba353`、`df57d3f`、`9393872`。 |
| 嵌套块 key 必须唯一 | 同消息内不同列表项的代码块也可能重名，必须把嵌套位置纳入身份，否则错行或状态串用。 | `6f56f1a`。 |
| 不要用 `ref(props.msg)` 固定住初次 prop | 列表复用、替换 prop 后，组件可能仍读取旧对象；应直接读取响应式 prop，或使用随 prop 更新的 computed。 | `98e713f`，并对照当前消息组件。 |
| 每个异步回包必须校验所属版本 | 会话、请求、消息、块、源码、主题或任务版本变化后，旧高亮或图片回调不能覆盖新内容；取消操作本身不能替代版本校验。 | `779cb3b`、`9393872`、`b9858cf`、`311e45a`。 |
| 图片加载状态不能直接决定业务展示模式 | 回收或重新挂载会使 loaded 重新变为 false，不能因此把完成图表切回源码。块闭合后锁存图片模式，实际失败才降级；用户手选源码也不应被异步回包覆盖。 | `49edb88`、`b82e385`。 |
| 同一已完成资源的复用不能重新阻塞整条消息 | 离屏图片未必再次触发 load，重复登记 pending 会让复制与工具栏永久消失；完成状态应按消息和资源身份记忆，资源改变才重新等待。 | `311e45a`，有真机日志和回归用例。 |
| 零高度的延迟行可能与虚拟列表回收相互影响 | 工具栏即使已经就绪，零高度列表项仍可能不出现。本项目为工具栏等待期保留最终高度，避免显示时再撑开列表。 | `311e45a`；属于本项目已复现的组合问题，不概括成所有零高度列表项都不可用。 |

## 四、图片、公式、图表和几何尺寸

| 注意事项 | 做错后的表现及应对 | 历史依据 |
| --- | --- | --- |
| 按块闭合决定生成时机 | 不能以源码达到某个长度、也不能只以整条消息完成判断图表/公式完成。过早生成会在源码和图片之间反复跳转，过晚又会等待整篇消息。 | `f1406c4`、`3f4f745`、`6b856ec`。 |
| 图片加载前先确定最终展示尺寸 | 保存原始宽高，按当前可用宽度预留高度；不要依赖图片 load 后才定高。否则恢复历史和快速输出会推挤后文。 | `4ebb39f`、`a960363`；当前 `image-layout.uts` 采用比例定高。固定正方形只是旧阶段方案，已被后续修正。 |
| 图片切换保留旧帧，并控制生成、解码尺寸 | 主题切换等场景用双缓冲，在新图片就绪后替换；避免高分辨率 SVG 不受限地栅格化。历史动态插入比预挂载更贵，但也不能把所有离屏大图永久挂载。 | `9ab3b92`、`14445cf`；其他分支还有 `1c3f813`、`fac069d` 的尺寸限制经验。 |
| SVG 不能只以浏览器效果判断跨端可用 | iOS CoreSVG、鸿蒙不同 SDK 的文字、CSS、tspan、marker 和图片源能力有差异。要走有版本隔离的兼容转换和缓存。 | `8440dc0`、`58e8704`、`5ed80bb`、`3a0bc41`。鸿蒙旧 SDK 下也不能无条件把含 text 的 SVG 直接转文件。 |
| 行内 SVG 与独立顶层 SVG 必须区分 | 按任意 `<svg>` 切成独立图块会在历史重建时把行内公式放大，并截掉段落文字。首次流式正常也不能证明恢复路径正常。 | `1989c6d` → `ec91d19`；修复同时提升快照版本，使旧错误快照失效。 |
| 主题和窗口变化必须使相关缓存失效 | 缓存不能仅按源码命中；主题、尺寸和兼容转换版本影响最终结果。原生条目若只回传空增量，仍可能显示旧主题 SVG。 | `13034e6`、`070e7f4`、`e4a605c`。 |
| 代码和表格的滚动内容宽度、内层宽度要一致 | 中间容器错误裁剪或 flex 收缩，会导致横向滚动已开启但长行末尾仍不可见；最终裁剪应由外部视口承担。iOS 有额外的显式宽度适配。 | `7b70d6c`、`179d0a8`、`7a196a3`。 |
| iOS 超宽原生内容必须考虑纹理物理宽度 | 本项目遇到逻辑宽度乘 pixelRatio 后超过 8192 的 Metal 纹理限制而崩溃，目前对代码和表格加了上限。上限是此实现的保护值，不是所有设备的通用 API 保证。 | `1d59b78`；当前代码保留该保护。 |
| 表格估算必须符合真实换行和边框规则 | 不换行单元格不能按列宽模拟折行；浮点列宽和底边贴边会因像素舍入产生空白或丢边。折叠屏、窗口变化后应更新相关尺寸。 | `ea500de`、`e4a605c`。窄表撑满还有 Web/小程序差异：`a1ac64d`、`4684fe3`。 |

## 五、Worker、跨语言边界和持久化

| 注意事项 | 做错后的表现及应对 | 历史依据与当前适用范围 |
| --- | --- | --- |
| Worker 先核对创建入口、目录声明和依赖 | Android 蒸汽模式通过 UTS 插件封装创建，manifest 声明 workers 目录；导入失败时检查平台入口与依赖声明。不要直接得出 Worker 不支持网络或原生插件的结论。 | `1111824` 的早期阻塞结论已被 `af54e20`、`212af74`、`da0b989` 和后续真实链路推翻。 |
| UI/WebView 操作回主线程 | 数据处理可下沉，Android `evalJS` 仍要调度回主线程，否则历史上发生过 WebView 崩溃。异步编码完成也需维持投递顺序。 | `ae3f45d`；当前 `proxy-web.uts` 仍显式切回 main。 |
| 跨线程、跨 UTS/JS 边界不能靠 `as` 变出实体类型 | Android 曾实际收到 UTSJSONObject，直接强转 RenderSnapshot 导致 ClassCastException；iOS ops、高亮结果也出现过对象字段丢失。应在具体边界采用明确协议、基础类型或 JSON 类型化解析。 | `1bb2cf2` → `141f571`；`b8ce9e8`、`1d59b78`。不是所有数据都要反复 JSON 深拷贝，而是不能删掉必要的边界转换。 |
| 回调寿命与通知方式按平台处理 | 不能把 Android 可持久监听的回调直接照搬到 iOS。iOS 曾因 UTSCallback 失效崩溃，当前网络数据和重建结果用有界生命周期的轮询读取；其他路径保留事件通知。 | `751066f`；其他分支 `a13d28e` 的“去掉轮询”不能覆盖后来 iOS 修复。 |
| 编译器会扫描非当前业务使用的 Worker 入口 | 平台隔离仅写在调用处可能不够，鸿蒙曾因扫描 Android 专用入口而缺少类；需要对应入口和类型边界。 | `6694e2a`、`b15b1f4`。模块迁移后内部相对导入也用于避免重复注册类型：`310a2f4`。 |
| 不假设 Worker 能直接调用所有 uni 存储 API | 鸿蒙依赖 UIAbility Context 的存储/文件 API 曾在 Worker 失败；后续使用鸿蒙原生文件接口把资源 IO 移回后台。 | `59dfb54` → `17dd680`。正确约束是选用该线程可用的 API，不能固化成“鸿蒙 IO 必须全部留主线程”。 |
| 最终快照要连同资源一起有效 | 记录格式版本、正文、主题、宽度、引用和资源身份；校验失败才重建，临时目录路径不能当永久资源。生成失败应保存终态降级，不要每次恢复重新失败。 | `a960363`、`e32f674`、`42ab880`、`ec91d19`；详见 [渲染快照说明](markdown-render-snapshot.md)。 |
| 所有缓存和资源都需要容量、去重与所有权规则 | 代码高亮按块隔离语法状态；图表和 SVG 合并同内容在途工作；限制缓存条目和容量。清理文件时保护仍被快照或本次运行引用的资源。 | `3dd641f`、`4658ee6`、`9983709`、`03ff96d`、`1bb2cf2`。 |
| 原生插件变动必须进入新基座 | 原生 Worker/UTS 插件实现、SO、xcframework 和依赖配置变更，可能需要重新打包自定义基座。页面热更新成功，不证明设备执行的是新原生实现。 | `3dd641f`、`1989c6d`、`311e45a`。排查时同时确认基座版本、插件产物和页面版本。 |

## 六、布局、滚动和平台入口

| 注意事项 | 做错后的表现及应对 | 历史依据 |
| --- | --- | --- |
| 列表与输入区使用明确的几何边界 | 绝对覆盖再按输入高度补位，容易形成滚动条落到输入框下方、正文底部被裁切、键盘后补位不一致。当前普通输入区与列表已改为正常上下布局。 | `cca7a74`、`4ae650f` → `5aa26cb`。 |
| 虚拟列表当前 scrollHeight 可能还是估计值 | 超大 scrollTop、交替底部锚点、初始化滚底都不能保证最终布局正确。新空列表曾因此追加内容缺失；一次测量也可能只到估算底部。 | `883df33`、`d1d8434`。本轮 `37ea853` 将点击校正限定为当前回复收尾、最多 16 秒，新增输出即取消；完整示例正常及冷启动后一次到底真机通过。 |
| 自动跟随与点击滚底是产品规则 | 早期多次修复自动跟随，不代表现在应恢复它。当前明确取消默认与持续跟随，只由用户点击执行一次滚动操作。 | `6535034`、`5b42f99`、`cd3775e` 的旧策略已被 `d1d8434` 替代。 |
| 持续输出的可见性检测不适合尾部防抖 | 每次内容增长都重置延迟，会让“可滚动了”的按钮一直等不到显示。应按视图提交合并检查，不必等流式停下。 | `a01ac66`；本轮安卓完整示例快速输出时已确认按钮及时可见。这里的圆形按钮与系统滚动条不是同一控件。 |
| 横向容器与侧栏都要明确手势归属 | 子容器声明横向方向，侧栏避免全页面抢手势；不要泛化为拦截所有 touchmove。后续 `f25f582` 在关闭侧栏时移除蒙板；本轮安卓十列表格、代码块横向及内部竖向手势均通过。 | `3dc1a7d`、`6f6993e` 是旧侧栏冲突的验收；不能代替当前问题的验收。 |
| 原生动画组件在列表内也有版本差异 | 鸿蒙 loading 曾在列表项内停转，后来在列表外绘制，按消息占位点的实际位置跟随，而不是固定在屏幕底部。 | `6ef11ca`、`3ae141b`。属于特定平台历史规避，不能扩成所有 loading 都移到外层。 |
| Vapor 生命周期和 CSS 不能照搬浏览器习惯 | 当前入口使用组合式生命周期。历史迁移收敛了组合选择器；旧鸿蒙多根页面还影响 selectorQuery。需要按目标框架版本核对支持范围。 | `07c82ab`、`2504761`、`d1304f4`、`a3f409f`。旧版“不支持某写法”不应无条件推广到当前所有平台。 |
| 小程序要单独考虑主包和运行上下文 | 不让 App/Web 的 Mermaid、MathJax、字体与高亮 WASM 无条件进入主包；轻量/完整版使用不同入口，语法缓存需版本校验，干净检出构建需主动创建目录。 | `87b1e63`、`17205ad`、`3e5abfb`、`121835a`。不能以开发机缓存下能运行代替干净构建验证。 |

## 七、不要重新引入的旧方案与误判

1. **把“等待一秒”当作渲染完成的判据。** 它只是已就绪之后的稳定期，不是代替资源完成通知的计时器。
2. **为避免卡顿全面暂停渲染。** 2025 年曾用滚动、菜单动画期间暂停发布来缓解竞争；当前架构已多次变化，不应直接恢复旧的 `canRender` 开关和固定一秒冻结。应先查实际重复工作和主线程成本。
3. **为了增量高亮给每行创建一个原生组件。** 数据增量和视图节点增量不是同一件事。
4. **为了减少 JSON 开销直接强转桥接对象。** 这个优化方向已经产生过真机类型崩溃，有明确反例。
5. **让公式统一经过 Base64 → PNG → 文件。** Android 后来改为行内 SVG，鸿蒙仍有单独资源准备。交付方式按平台与当前解析器决定，旧转换链不应统一恢复。
6. **以源码长度猜图表完成，或给所有图表固定正方形。** 后续分别改为块完成态与按原始比例预留尺寸。
7. **认为禁用轮询对所有平台都正确。** 当前 iOS 的轮询承担回避回调生命周期崩溃的职责。
8. **认为静态正确、编译通过就等于视觉或性能正确。** flatten 语义丢失、图片恢复错位、跨线程强转、复用后任务卡死，都曾越过前面的检查。
9. **把历史框架缺陷当成当前版本保证仍存在的事实。** 圆角裁剪、RichText 位图更新、鸿蒙 SVG 等均有明确环境范围；升级后应依据最小复现判断是否仍需规避。

## 八、历史证据应怎样使用

历史性能报告支持的判断是：原生布局、RichText 更新、图片解码和 View 追加曾是重要瓶颈；减少 JS 耗时不一定降低长帧。应保持设备、基座、视图目标、正文、输出节奏、冷暖启动和采样区间可比，再比较帧耗时分布、卡顿帧与内存。

`5ef970c` 的十类元素测试里，公式采用整块发送，其他元素采用细粒度流式，不能据此直接认定公式普遍更快。`a133b29` 已记录单独下沉 HTML、调整 Worker 到 32ms 未证明独立收益；`df0d7aa` 也明确没有额外帧性能收益。高频日志本身还会放大 UI 开销：`9b3c037` 关闭代码节点日志；其他分支的 `869d4ba` 关闭携带全量尾块的日志。

原历史整理只包含记录和静态抽查；本轮另外完成安卓真机功能回归，没有重新采集帧性能数据。详见 [消息顺序渲染方案及真机记录](message-render-order.md)。


## 九、本轮新增约束

- 发布展示版本与完成状态必须有顺序：先取消已完成状态，再发布新版本，最后发布实际完成状态。原生同步 watcher 可能在每一次赋值后运行；先完成后版本会冻结旧内容。`aef43ea` 有同步观察者测试与真机故障注入证据。
- 准备任务必须有失败终态并释放回调；超时后拒绝迟到回包，不能让工具栏永久等待。`29ba66e` 覆盖公式共享在途与图表失败。
- 图片首次终态属于消息与资源，而非回收组件；失败源码必须能放行后文。`9c7ab55` 真机验证公式、图表图片加载失败后的收尾。
- 严格顺序须以展示准备完成为界。只冻结字符串而放任前方图片后来加载仍不足够；`2a280ff` 在连续就绪前缀上发布后文。未知远程图片、跨重启事件轮次及阅读锚点仍有边界。
- 设备功能验收通过不等于没有框架异常。当前隐藏 WebView 首次挂载仍存在原生布尔桥接空值异常，保留诊断并撤回未奏效的属性补丁，不用猜测性代码掩盖问题。
